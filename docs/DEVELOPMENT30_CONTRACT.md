# Новый development benchmark: протокол до расчёта ошибок

Зафиксирован 2026-09-07 после проверки доступности каталогов JPL, до загрузки
траекторий новых объектов и до просмотра ошибок кандидатов. Это development
train/validation, а не финальная проверка. Пользователь разрешил начать этап.

## Отбор и разделение

- 30 новых нумерованных астероидов: по пять сближений с Землёй, Венерой,
  Марсом, Юпитером и по пять внутренних/внешних контрольных орбит главного пояса.
- Каталог CAD: 2026-01-01 — 2029-12-31, numbered asteroids, `neo=false`.
  Для Земли/Венеры/Марса доступный диапазон 0.2 AU, для Юпитера 0.5 AU.
  Последний содержит ровно пять событий пяти объектов на момент выгрузки.
- В каждой планетной группе берём пять уникальных объектов с наименьшим
  каталоговым расстоянием; при равенстве — JD и номер. Повторный объект
  исключается во всех следующих группах. Порядок групп записан в конфигурации.
- Контроли: первые 1000 результатов SBDB, отсортированные по `spkid`, с
  `a` 2.1–2.5 AU, `q>1.8 AU`, `e<0.2` либо `a` 3.0–3.4 AU,
  `q>2.5 AU`, `e<0.2`. Из этого ограниченного пула берём пять по SHA-256
  от seed, группы и номера. Это удобная выборка, не оценка популяции.
  Слово «контроль» не утверждает отсутствия всех возмущений или событий.
- Исключаем старые шесть просмотренных объектов и 16 массивных астероидов,
  используемых в force model; так исключена собственная сила на объект.
- Внутри каждой группы отдельный SHA-256 split-порядок: три train, два
  validation. Все горизонты одного объекта остаются вместе. Итого 18/12.
  Одно основное событие на объект, поэтому это одновременно удержание событий.
- Старт: полночь TDB за 30 суток до календарной даты события; для контролей
  2029-01-01. Горизонты 7/30/90/180/365 суток. Метаданные CAD используются
  только при выборе окон и оценке; не передаются селектору.
- Финальный test не выбран. После первого просмотра validation его нельзя
  использовать как неизменённый финальный test последующих доработок.

## Эталон, силы и численность

Inputs: один начальный state Horizons, TDB start, горизонт, допуск, известные
эфемериды возмущающих тел и константы. Все rollout рекурсивные. Никаких будущих
состояний астероида, orbit-fit параметров NG, номера/группы/split среди признаков.
Horizons — модельный teacher; текущая орбита может включать более поздние
наблюдения. Это условное распространение заданного состояния, не исторический
прогноз по реально доступным на тогдашнюю дату наблюдениям.

Общие координаты: Sun body centre `500@10`, ICRF/FRAME, геометрические векторы
без aberration/light time, TDB, AU и AU/day. Все девять планетных возмущателей
из pilot (восемь планет/систем плюс отдельная Луна) загружаются на одной
равномерной часовой сетке 2025-12-01 — 2030-12-31. Между узлами cubic Hermite.
SB441-N16 остаётся на существующей ежедневной сетке. Новые исходные ответы
неизменяемы, сохраняются URL/signature/SHA-256/размер. JPL запросы последовательные.

Кандидаты: B2; B3; B3+GR; B3+GR+SB16. Каждый выбирается на весь rollout.
Это намеренно ограниченный набор; Earth J2, полный EIH и NG не добавляются
в этот этап, их сильные события проверяются отдельно. Старые B0/B1 sanity
baselines остаются в инженерном пилоте. Добавление сил не обязано улучшать
согласие с teacher; отсутствие подходящего кандидата сохраняется.

Production RK4: прежнее правило изменения шага по предсказанным расстояниям,
default 1/16 суток × 0.5; offline fine × 0.5. Ежедневные outputs и все
принятые endpoints сохраняются для последующей интерполяции оценки. Референс:
ежедневная сетка плюс 5 минут в ±2 суток вокруг выбранного события.
Эта дополнительная сетка **не передаётся интегратору**: error evaluator
интерполирует уже рассчитанную траекторию. Minima всех девяти тел вычисляются
по эталонной общей сетке, с явными ограничениями интерполяции и окна.

Достаточность: max position error на оценочной сетке ≤ 0.1/1/10 km и
max production/fine difference ≤ 10% допуска. Это чувствительность к шагу,
не строгое численное доказательство; межузловой максимум не гарантирован.
Ошибки скорости/RTN и closest-approach distance/time сохраняются отдельно.
Сходимость внешних эфемерид, независимый solver и неопределённость начального
состояния этим опытом не сертифицируются.

## Правила и стоимость

До validation сравниваем fixed candidates и два простых правила:

1. Horizon rule: для каждого горизонта/модели максимум train effective error
   `max(position_error, numerical_difference/0.1)`. Выбор самого дешёвого
   по train median runtime кандидата, укладывающегося в допуск.
2. Physics rule: B2 preliminary trajectory, геометрия всех планет, minimum
   solar distance, максимумы отношения возмущения к солнечной силе и
   `∫(H-t)|a_omitted(t)|dt` в km для планет, solar GR и SB16. Это proxy,
   не оценка с учётом state transition и не error bound. Для B2/B3/B3+GR
   train-only коэффициент ≥1 покрывает максимальное отношение effective
   error к proxy (floor 1e-6 km). Для последнего кандидата — empirical
   train maximum по горизонту. Геометрия сохраняется для анализа следующего
   поколения правил; в этой версии численный score использует force proxies.

При отсутствии предсказанно допустимой модели возвращается последний кандидат
с `fallback=true`, без обещания точности. Его фактические нарушения учитываются.
Артефакт коэффициентов и его hash фиксируются **до запуска validation**.
Правила не пересматриваются после просмотра validation в рамках этого опыта.

Три последовательных повтора. Сначала train, затем freeze, затем validation.
Время propagation по каждому горизонту — причинный prefix годового rollout,
никакая последующая часть не входит в prefix. Features считаются отдельно
для каждого H. В отчёте отдельно resident-data timings, shared load,
features/inference/propagation. На validation дополнительно прямые вызовы
selected rollout измеряют полную стоимость. Offline oracle — только
диагностика предела экономии и не результат работы селектора.

Показываем все случаи, число нарушений и no-candidate, выбор моделей,
полную стоимость; экономию сравниваем на одинаковых случаях. Отдельные
объекты/события, а не вложенные горизонты — единица независимого наблюдения.
12 validation объектов не дают статистической гарантии редких отказов.
