# Общая модель с относительным временем

Уточнение 2026-09-09: optional J3/J4 — явная физическая гипотеза. Для saved
Apophis teacher указан Earth J2 only, поэтому включение высших гармоник
не является гарантированным улучшением его воспроизведения. Отдельный
[аудит соглашений](APOPHIS_GRAVITY_CONVENTIONS_REPORT.md) не меняет этот
frozen API или его прежние scores.

`src/relative_force_model.py` собирает подробную модель сил;
`src/forecast_precise.py` строит прогноз из одного начального состояния.
Это отдельная версия рядом с frozen v2, без маршрутизации по ID астероида.

Обязательная физика этого подробного кандидата: Солнце, все переданные
точечные perturbers, solar Schwarzschild, Earth J2. Дополнительные J3/J4
включаются явно. В исследовательском runner передаются девять planet/system
perturbers и SB16. Отсутствующий perturber не возникает автоматически.
Это API одного подробного кандидата, а не замена всей лестницы B2/B3/GR/SB
или новый автоматический selector.

## Входной контракт

- Initial position/velocity: Sun-centred ICRF, geometric AU и AU/day.
- Origin: JD TDB и соответствующий TDB calendar label при подготовке
  ephemerides. Calendar labels нельзя преобразовывать как UTC.
- Planet/SB ephemerides: `Perturber` с `RelativeEphemerisInterpolator`;
  относительные дни от **того же** origin, покрывающие весь прогноз.
- Константы и Earth coefficients передаются явно с provenance у вызывающей
  программы; API не скачивает данные и не выбирает значения по имени тела.
- Необязательный `NGInput` содержит коэффициенты, источник, время
  доступности и, если известно, uncertainty. `ng_policy="available"`
  проверяет доступность на старте; `"required"` отказывает без неё;
  `"off"` явно отключает NG. Отсутствие A2 не является измеренным нулём.
- Будущая траектория астероида и даты эталонных событий в API отсутствуют.

## Вызов

Ниже шаблон для уже подготовленных входов. `initial`, `relative_planets`,
`ng_input`, `mu_sun`, `c`, `earth_j2`, `earth_zonals` берутся из входного
пакета с проверенными единицами и происхождением, а не из будущего teacher.

```python
from forecast_precise import forecast_precise

states, meta = forecast_precise(
    initial=initial,
    origin_jd_tdb=origin_jd_tdb,
    horizon_days=365,
    planets=relative_planets,
    constants={
        "mu_sun_au3_d2": mu_sun,
        "speed_of_light_au_d": c,
    },
    config={
        "earth_j2": earth_j2,
        "earth_zonals": earth_zonals,
        "ng_policy": "available",
        "dopri54": {
            "rtol": 1e-13,
            "atol_position": 1e-15,
            "atol_velocity": 1e-16,
            "max_step": 0.25,
            "min_step": 1e-10,
            "max_steps": 1_000_000,
        },
    },
    ng=ng_input,
    solver="dopri54",
    enabled_j3=True,
    enabled_j4=True,
)
```

Для независимого алгоритмического сравнения установить
`solver="compensated_rk4"` и передать в config:

```python
"compensated_rk4": {
    "default_step_days": 0.0625,
    "step_scale": 0.25,
    "max_steps": 1_000_000,
}
```

Размер RK4 шага дополнительно ограничивается существующим encounter
selector по предсказываемому текущему состоянию и положениям perturbers.
Это изменение **численного шага**, не переключение физической модели.

Возвращаются состояния на днях 0..365 и все принятые внутренние точки
в `meta["accepted_endpoints"]`. Для дробного горизонта добавляется его
точный конец после целых суток. Metadata содержит состав сил, NG status,
численные настройки, статистику шагов и координатный контракт.

DP в этом API запускается на последовательных суточных интервалах с
переносом только рассчитанного состояния и локальным временем от нуля.
Контроллер шага перезапускается каждый день; общий step budget учитывает
все интервалы. Это зафиксированная деталь API, поэтому его trace не обязан
совпадать с одним непрерывным DP вызовом Apophis audit. Никакого нового
наблюдаемого состояния на границах суток не вводится.

`precise_dopri.py` — отдельная экспериментальная compensated DP версия из
[численного аудита](PRECISE_PROPAGATION_REPORT.md). В текущем 132-run
regression она не подменяет DP backend API.

## Ограничения и проверка

J3/J4 используют прежнюю IAU mean-pole/IERS secular approximation; это
не полная земная геопотенциальная модель с EOP, tides и tesseral harmonics.
Время/GM scaling approximation явно отражена в metadata. Обоснование и
источники коэффициентов: [предыдущий force audit](APOPHIS_SHAPE_WEAK_FORCE_REPORT.md).

`accuracy_guaranteed=False` и `uncertainty_propagated=False` имеют буквальный
смысл. Выбор кандидата под допуск, отказ при недостаточности всей лестницы
моделей и распространение неопределённости требуют отдельных компонентов.
Полная shape/spin/thermal модель также требует отдельного входного пакета;
добавлять тепловую отдачу поверх уже описывающего её nominal A2 нельзя.

Общий builder в baseline и J3/J4 ветвях даёт **точно те же ускорения**,
что и прежний Apophis audit, на 797 сохранённых прогнозных состояниях.
Проверка переносимости: [контракт 30 объектов](RELATIVE_FORCE_REGRESSION_CONTRACT.md).
Воспроизводимый runner: `src/run_relative_force_regression.py`;
offline verifier: `src/verify_relative_force_regression.py`.

## Следующее расширение для формы

Прямая поправка к движению центра масс от конечного размера тела и
зависимость тепловой отдачи от формы/вращения — разные компоненты.
Следующий отдельный эксперимент должен сначала проверить доступность
spin state, соответствие его body frame геометрической mesh, density и
thermal parameters. Предварительная PDS Model B сама по себе этого не задаёт.

Для sensitivity analysis нужны заранее заданные допустимые варианты
ориентации/вращения и физических параметров, одинаковые initial/reference
и recursive rollout. Номинальный A2 остаётся контрольной моделью; явная
тепловая модель должна заменять соответствующий вклад или иметь явно
определённый остаточный смысл. При неизвестной uncertainty коэффициента
нельзя объявлять произвольный диапазон A2 измеренным доверительным интервалом.

Сначала оценить, меняются ли ошибки и достаточный кандидат при допусках
100 m/1 km; затем решать, оправдан ли более дорогой физический расчёт.
Для раздельной двойной системы дополнительно нужен контракт того, что
прогнозируется: барицентр или конкретный компонент, и его относительная орбита.
